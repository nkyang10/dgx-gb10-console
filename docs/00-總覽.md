# DGX Spark 集群 HTTP 狀態 API — 總覽與索引

> 目標：做一個 HTTP API，畀另一部機用 HTTP 攞到 **2×DGX Spark（GB10 Grace Blackwell，DGX OS Ubuntu 24.04 ARM64，統一記憶體）** 嘅狀態。
> 狀態分三大類：**硬體**、**軟體/系統**、**vLLM（行緊嘅 software）**。
>
> **本區係文件總覽**：研究結果已按 **data category** 拆開，每類一個 MD。寫 collector 嗰陣直接睇返對應嗰份。
> ⚠️ **儲存/API 呈現方式未定** —— 等用戶揀（見「下一步」）。本機只備內容，唔裝唔 test。

---

## Assumptions（設計假設）

1. **vLLM 喺 Docker container 入面行**（Docker + NVIDIA Container Toolkit，DGX OS 內建）→ 用 `docker ps` 偵測 vLLM container、攞佢 publish 出嚟嘅 port，再 HTTP 撈佢 `/metrics`+`/health`+`/v1/models`。**唔當** bare-metal `vllm serve`。
2. N 節點 cluster（2 部=基本部署），一部 aggregator 拉晒 `nodes[]`。
3. 每部機都行 `nvidia-smi` / 官方 driver + 可選 `nvme-cli` / `lm-sensors` / `ethtool`（缺咗 graceful degrade）。
4. Fabric（ConnectX-7 RoCE）淨係畀 NCCL/compute，status API 經 10GbE mgmt IP 拉。
5. 本機只備內容，唔裝唔 test；完成後搬去 DGX 由用戶安裝。

## 0. 平台最關鍵事實（影響成個設計）

| # | 事實 | 影響 |
|---|---|---|
| 1 | **DGX Spark = GB10 Grace Blackwell Superchip**，128GB **統一記憶體 UMA**（CPU 與 GPU 共用同一 LPDDR5x 記憶體池） | GPU 冇獨立 VRAM → 記憶體監測唔好靠 nvidia-smi |
| 2 | **nvidia-smi 記憶體字段報 `Not Supported`/`N/A`**（iGPU 無 framebuffer） | 記憶體要用 `/proc/meminfo`+`free -h`（官方認可） |
| 3 | ❌ **NVIDIA 官方「無計畫支援 DCGM on Spark」** | dcgm-exporter/dcgmi 靜默失敗，**唔好用** |
| 4 | ❌ **tegrastats 預設唔存在於 DGX OS**（JetPack/Jetson 專用）；jtop/jetson-stats 依賴 tegrastats → 唔可靠 | 以 nvidia-smi + hwmon 為主 |
| 5 | **可靠 GPU 字段**：name、driver_version、pstate、utilization.gpu、temperature.gpu、power.draw、power.limit、clocks.sm/graphics | GPU 狀態主力 |
| 6 | 溫度/整機功率用 **hwmon**（社群 `antheas/spark_hwmon` 驅動，暴露 tj_max/gpu/soc zone、sys_total/gpu power rails） | 健康/功耗監測 |
| 7 | 網絡：**10GbE RJ-45**（管理/外網）+ **ConnectX-7 200G**（fabric，multi-host 模式 → 4 個接口）；**GPU Direct RDMA 唔支援** | fabric 用 RoCE + HCA counters |
| 8 | **vLLM `/metrics`（Prometheus）+ `/health` + `/v1/models`** 係攞 vLLM 狀態嘅正路 | 另一部機可直接撈 |
| 9 | NVIDIA 官方整合監控介面 = **DGX Dashboard**（本機 `http://127.0.0.1:11000`，SSE + 登入） | 可作 GPU/UMA 補充（見 狀態-01） |

來源：NVIDIA DGX Spark System Overview + Known Issues、NVIDIA forum（DCGM/tegrastats/Beszel）、GitHub 多個 monitoring repo。

## 5. 推薦 API 架構（供用戶揀儲存/呈現方式時參考）

| 方案 | 做法 | 取捨 |
|---|---|---|
| (a) FastAPI REST | `/health`、`/status`、`/vllm`、`/metrics.json`... 回 JSON；psutil | 快、易讀、好 debug；subprocess 多會慢（要 cache） |
| (b) Prometheus exporter | 每節點一個 `/metrics`（node_exporter-style）被 scrape | 原生 Grafana/PromQL；適合 dashboard/alert |
| (c) Prometheus + Grafana | 兩節點 exporter + dashboard | cluster 標準，但想要淨「狀態頁」就 overkill |
| (d) Poll vs Push | HTTP polling vs WebSocket/SSE | **polling 簡單+cache-friendly；SSE/WS 只有想要低延遲 live 先需要** |
| (e) Cache | ~3–5s TTL JSON snapshot；collector async | 唔每次 request 都 spawn subprocess |
| (f) Auth | BasicAuth/API key；bind 10GbE/mgmt LAN；mTLS | exporter 低端口；remote 用 reverse proxy gate |
| (g) **N 節點** | **一部 aggregator 拉晒 `nodes[]` 其餘（星型）**，合併出 `/health`+`/cluster.json`；每部都係一等公民跑 exporter；N 大時用 Prometheus federation / 多級 aggregator | 單 aggregator + N leaf 最乾淨；詳見 [實作-多節點擴展](實作-多節點擴展.md) |

**推薦藍圖**：每節點一個 exporter daemon（FastAPI 或 Go）行喺 node-local port；**一部 aggregator** 經 **10GbE mgmt IP**（唔用 ConnectX fabric）拉晒其餘節點合併；cached ~3–5s；vLLM 每節點按 `nodes[].vllm_port` 撈；alert-worthy：NVMe critical_warning/percentage_used（此平台有 known 故障）、ConnectX phys_state≠Up、rdma link down、disk>85%、systemctl failed、GPU throttled、temp 接近 96–97°C。
