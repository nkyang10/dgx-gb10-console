## B — vLLM 深觀察

### B1 · Per-request OTel tracing（🔵 唔急）
- vLLM 有 OTLP：`--otlp-traces-endpoint http://jaeger:4318` + `--collect-detailed-traces all|model|worker`。⚠️ 係 **`otlp`** 唔係 `oltp`（docs typo）。
- Span 有 `gen_ai.latency.time_in_scheduler/model_forward/model_execute`；detailed 先有 `vllm:model_forward_time_milliseconds`/`model_execute_time_milliseconds` histogram。
- **結論：對 status API，histogram P95（已 scrape）就夠、零成本。Tracing 只有你喺跑 Jaeger/Tempo 想 request-level waterfall debug 先值得（~0.5day + infra）。**

### B2 · Live per-request / queue view
- **`/load`** → `{"server_load": ...}`：
  - current `main`：**integer** = 用緊 GPU 嘅 in-flight req（`--enable-server-load-tracking`）
  - 舊 stable：dict `{num_requests_running, request_ids_running[], num_requests_pending, request_ids_pending[]}` — **版本敏感，要對返 image**
- **冇 built-in per-request live 端點**。最近似：
  - `/metrics` gauges（`num_requests_*`）
  - `--enable-per-request-metrics` → response 加 `metrics:{ttft, generation_time, queue_time, mean_itl, tokens_per_second}`
  - `--enable-log-requests` → 每 request 一行 log 去 **stdout**（id/model/tokens/timing）—— 最平 per-request ledger，scrape container stdout
- effort：`/load`+gauges ~0.5d；per-request JSON/logging 要 flags+parse。

### B3 · Per-model SLO（🟢 已有 label，零功夫）
- 每個 vLLM metric 都有 `model_name`+`engine` label → 直接 PromQL 分組：
  - tok/s：`rate(vllm:generation_tokens_total[5m])`、`rate(vllm:prompt_tokens_total[5m])`
  - latency avg：`e2e_request_latency_seconds_sum/_count`；P95：`histogram_quantile(0.95, sum by(le)(rate(..._bucket[5m])))`（同 TTFT/TPOT）
  - backlog：`num_requests_waiting`（+`_by_reason`）
  - **goodput 冇官方 metric**：proxy `tokens/s × (1 − abort share)`，abort=`request_success{finished_reason="abort"}`
- effort：~0.5d（淨 PromQL+Grafana）。

### B4 · Engine sleep + KV-block 深
- `vllm:engine_sleep_state{model_name,engine,sleep_state=awake|weights_offloaded|discard_all}`：awake=1 先係醒；三隻都 0=sleeping；level1 weights_offloaded、level2 discard_all。
- **KV 指標要 `--kv-cache-metrics-sample`**（default 0.01=1% 採樣）：`kv_block_lifetime_seconds`、`kv_block_idle_before_evict_seconds`、`kv_block_reuse_gap_seconds`。
  - **睇到乜**：大 lifetime + 大 idle-before-evict = stranded/underused cache（prompt tail pinned）；細 reuse gap = healthy prefix churn。有助 tumm KV size。
- effort：pass flag 就得（樣本 overhead 好細）。

### B5 · Ray cluster health（🔵 跨節點 Ray 先行）
- `http://<ray-head>:8265`（dashboard + `/metrics` if `RAY_PROMETHEUS=1`）；`ray status`（node/resource/worker RUNNING）
- key series：`ray_node_gpus_used/available`、`ray_cluster_active_nodes`、`gcs_server_*`、`ray_node_cpu_*`；health = 全部 worker RUNNING + gpus_available>0。
- effort：expose 8265 + scrape ~0.5d。

### B 推薦優先：**B3（0 功夫）→ B2 /load+gauges → B4 `--kv-cache-metrics-sample` → B5 Ray → B1 defer**

## C — 主動基準測試（⚠️ 只有唔 serving 先可以 run）

> 底線：**C1/C2 永遠唔好喺 serving 時 run**（sat DW PCIe/memory/NCCL path）→ 放**靜音維護時段**（e.g. 清晨 cron，一日一次）。C3 稀疏、C4 被動先可以 live。

### C1 · Fabric bandwidth（perftest）—— 🟥 最危險（sat 度 NCCL 用緊嘅 PCIe path）
- `ib_write_bw -d mlx5_<iface> -R -x <gid> -s 1M -t 10`（server background）＋ client 對 `nodeB_ip`；`ib_read_lat` 度 latency。要 **root** + `rdma-core`。
- DGX multi-host = **4 logical iface** → 揀對應 peer port/root-complex，用 `-d` pin HCA。
- **現實 ~100–110 Gbps**（vs 200G wire）＝**唔係故障**：GB10 fabric path = PCIe Gen5×4 ≈ 100–112 Gbps ceiling。係 `<<90 Gbps` 或 read/write asymmetry >15% 先當 fault。
- Cadence：**OFF while NCCL/inference**；gate `pgrep -f nccl`/vLLM proc；一日一次 5-min。

### C2 · Memory bandwidth（273GB/s）
- `stream`（`/usr/bin/stream`，single-copy single-core）≈270GB/s；`bandwidthTest`（CUDA）都係同一個 pool。
- **兩樣都 load 緊 compute/memory** → 唔好 serving 時 run；要 active 數就同 C1 一樣靜音窗（`OMP_NUM_THREADS=4 ./stream`，讀 `Triad MB/s`）。**預設被動**（睇 mem-clock/DGX Dashboard UMA/vLLM throughput）。

### C3 · Tiny live TTFT probe（🟡 唯一可以 live 嘅主動 probe）
- `curl --max-time 15 localhost:8000/v1/chat/completions -d '{"model":"...","messages":[{"role":"user","content":"hi"}],"max_tokens":1,"temperature":0}'`
- 度 real TTFT = 1-token request 首 byte time；**但 vLLM 自己嘅 `time_to_first_token_seconds` histogram 更好（被動零騷擾）**。
- ⚠️ 探針會食一個 queue slot（busy 時係 latency tax）；**疏——每 60–120s 一次封頂**，唔好 flood。

### C4 · GPU throttle 主動檢查（🔵 唔好用 active 工具）
- `spark-gpu-throttle-check`（hoesing）**會 load GPU** → **唔安全 while serving**。
- **被動更啱**：vLLM 真實 load 時淨係睇 `nvidia-smi --query-gpu=pstate,utilization.gpu,clocks.sm,clocks.max.sm,temperature.gpu,power.draw,power.limit`；`clocks.sm <0.45×max` + util高 = 節流/USB-C PD fault（見 狀態-09）。**零騷擾、最快。**

### C 總結
- **Live 可做**：C3（稀疏）+ C4（被動，fold 入 resident 2–5s tier）
- **靜音窗先做**：C1 + C2（一日一次）
- 全部喺 maintenance 窗 + gate「有冇 NCCL/vLLM」
