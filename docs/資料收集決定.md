# 資料收集決定清單 — 邊啲數據有用（合併 10 個 GitHub repo 深研）

> 目的：從 10 個 DGX Spark 監測 repo 深研，篩出**值得收嘅數據**。
> 每個資料列明：**點攞**（指令/sysfs/NVML）+ **證明哪個 repo 做到** + **優先級**。
> 製作方式：10 條平行 thread 逐個讀實際源碼（sparktop / sparkDash / nv-monitor / spark-dashboard / Sparky / spark-smi / sparkview / sparkscope / spark-mon / dgx-spark-observability）。

---

## 0. 三大關鍵共性（10 個 repo 一致確認）

1. **GPU 記憶體（VRAM）喺 GB10 係 N/A** → 全部要 fallback：
   - `used` = Σ `nvidia-smi --query-compute-apps=used_memory`（各 process MiB 加埋）
   - `total` = `/proc/meminfo` 嘅 `MemTotal`（UMA：GPU pool == host RAM）；`free` = MemAvailable
   - 要加 `vramUsedIsDerived` flag（sparktop / sparkDash / observability / nvidia-textfile sidecar 一致做法）
2. **vLLM 狀態正路 = 撈 `:8000/metrics`（Prometheus）+ `/health` + `/v1/models`**；`/proc/net/dev` 喺 RoCE 睇唔到 fabric 流量
3. **本地收集 vs 遠端**：遠端一律 **單一 batched SSH script**（`---SECTION---`/ASCII-RS 分隔）一次過攞晒，唔好每 metric 一開 ssh

## 8. ✅ Recommended 最小集（我哋個 2 節點 status API 應收）

**必備（fast tier 2–5s）**：GPU util/temp/power/clocks/throttle + GPU 記憶體(derived) + CPU usage/loadavg + RAM(UMA) + thermal zones + netdev TCP + **RDMA fabric** + vLLM(status/models/metrics) + systemd/docker/ports + node reachability probe

**慢 tier（30–60s）**：`ethtool -S`(hw counters)、fabric 深、systemctl inventory、disk fs 用量

**最慢（60–120s）**：NVMe SMART、hardware inventory

**可選（🟡）**：DGX Dashboard SSE（官方 UMA）、ECC、PSI、spbm 功率 rails、GPU processes、load 1/5/15 全

**Skip（太重/低值）**：完整 docker inspect env tree、graphics proc table、autodetect endpoint 掃描、N×M cartesian SQLite、cAdvisor/Loki 全堆（對純 status API 過重）、Grafana 38 panel（要 dashboard 先另加）

## 9. Alert 閾值（直接採用 observability 14 條 + sparktop 補充）

| 警報 | 邏輯 | 嚴重度 |
|---|---|---|
| HostMemoryCritical | RAM>95% + swap 重度用，`for:5m` | crit |
| HostMemoryHigh / DiskHigh | >85%，15m/10m | warn |
| DiskCritical | `/`、`/var`>95% | crit |
| GpuTempCritical | `DCGM_FI_DEV_GPU_TEMP>80`（我哋用 nvidia-smi temp）`for:2m` | crit |
| **GpuMemoryHigh** | (Σcompute-apps / MemTotal)>0.90 `for:10m`（UMA） | warn |
| **GpuThermalThrottle** | `nvidia_gpu_throttle_active==1`（thermal+power-cap）`for:5m` | warn |
| **SMClockCollapse**（USB-C PD 故障） | `sm_clock/sm_clock_max < 0.45` **AND** util>50% **AND** power<35W **AND** throttle_reasons==0（hysteresis on≥55%/off<45%）`for:2m` | crit |
| NvmeCriticalWarning / NvmeMediaErrors / NvmeAvailableSpareLow | SMART 數值閾值 `for:0m` | warn/crit |
| NodeExporterDown / 節點 down | `up==0`（連帶 inhibit 同 host 其他 alert） | crit |
| Fabric link down | `phys_state!=Up`、`state!=ACTIVE`、RDMA faults delta>0 | crit |

## 10. 最值得偷嘅工程模式（10 repo）

1. **batched SSH script + `---SECTION---`/ASCII-RS framing**，一次 exec 攞晒、check=False 唔逐 section 失敗（sparktop/sparkscope/spark-mon）
2. **unified-memory modeling**（total=sys pool、used=Σprocs、derived flag）（sparktop/observability）
3. **RDMA ∑**：`ethtool vport_rdma` prefer、fallback IB counters×4（sparktop）
4. **in-memory `ClusterSnapshot`** → `/metrics`+`/api/snapshot`+WS 全部係同一個 snapshot 嘅 cached projection（sparktop）
5. **capability-driven probing**：detect 一次入 caps dict、冇 sensor 就 skip、唔造假 0%/N/A（spark-smi）
6. **Pydantic JSON envelope** `ClusterMetricsResponse{schema_version, nodes:[NodeMetrics{node_name,status:online|offline,cpu,ram,gpus,disks,power,error_message}]}`，全部 Optional→null 唔 fail（spark-mon）
7. **Optional X-API-Key auth**（`APIKeyHeader(auto_error=False)`，設咗 secret 先 enforce）；/health 唔 auth（spark-mon/sparktop）
8. **WS broadcaster** with per-client timeout + dead prune（sparkscope）
9. **textfile-collector sidecar pattern**：細 bash/python loop 寫 textfile→node_exporter 攞（observability）
10. **3-consecutive-sample alert policy** + hysteresis（sparkscope/sparktop）

## 11. 結論一句

**照住 spark-mon 嘅 API shape（Pydantic envelope + offline + optional auth）＋ sparktop 嘅 snapshot/丟取/batched 模式＋ observability 嘅 alert 閾值，收 §8 個最小集** → 就係一個穩、平、全面嘅 2 節點 DGX status API。
