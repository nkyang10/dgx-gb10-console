Product Briefing

DGX GB10 Console

DGX Spark 集群　即時狀態 × 效能 × 健康監控平台

一部 HTTP API，實時睇晒你部 DGX 做緊乜 — 硬體、軟體、vLLM 推理效能、成本、告警。

適用 2 至 N 部 DGX Spark（GB10 Grace Blackwell）

客戶痛點

你很銀緊部 DGX，但「佢喺度做緊乜？」

無可視化 → 過熱降頻、OOM、排隊爆煲、磁碟滿、成本失控，全部唔知

  • 只知部機「着咗」，但唔知 GPU 係咪過熱緊→降頻，效能偷偷流失
  • vLLM 排緊幾多 request？TTFT 有冇爆炸？邊個 model 最撬樽頸？
  • 磁碟幾時滿？NVMe 幾時壞？能耗同 Token 成本每月幾多？
  • 要逐部 SSH 睇 nvidia-smi，N 部機睇到頭都大
  • 出事先發現 — SLA／收入無形損失

硬體健康

過熱降頻，一眼睇到

GB10 統一記憶體(UMA) 專屬做法 — 唔靠報 N/A 嘅 nvidia-smi VRAM

  • GPU：util / 溫度 / 功率 / 時脈 / throttle reason（熱 vs 功率 vs 卡死）
  • 熱降頻觀測矩陣：溫度 + SM 頻率比率 + throttle bit + 負載，夾埋判
  • CPU / 記憶體(UMA) / 磁碟(O-NMe SMART) / 網絡(fabric RDMA)
  • 節流史 timeline：幾時降頻、持續幾耐 — 自動入告警
  • GB10 罕有「卡死低時脈」bug 偵測（USB-C PD 供電問題）
temp>80 + clock 低 + thermal bit過熱降頻熱
power_cap bit set功率上限（非熱）功率
clock < 45% + 無 reason + util 高卡死 bug（供電）卡死
vLLM 效能 — 個 API 真正主角

唔止睇硬件，睇緊推理點運行

  • 吞吐：decode / prefill tok/s，RPS（完成 request 率）
  • 延遲：TTFT、ITL/TPOT、e2e — avg + P95（窗口度率，唔抄即時數）
  • 積壓：running / waiting 隊列、per-model backlog、queue time
  • KV-cache 用率、prefix-cache hit rate、preemption
  • per-model SLO goodput；engine sleep / idle / dead 狀態

想知佢有冇排隊？

num_requests_waiting ↑ ＋ queue_time ↑ ＝ 積壓緊、處理緊 ——
唔係掛咗，係 vLLM 自己排隊消化緊。

成本透明 · 容量先知

幾多電、幾多 Token、幾時滿 — 全部數字化

  • 能耗：整機 wall power（spbm），kWh/日，電費（$/kWh）
  • idle vs active 成本分帳：幾多電係白拏
  • Token 會計：per-model 每日 tokens、$/1M tokens、cache 慳幾多
  • 預算告警：$ 突破 80% / 100% 即知

容量預測

  • disk TTF：幾時 full（4h / 6h 預警）
  • KV / 記憶體 headroom 趨勢（UMA）
  • 「要唔要加 node」有數據答
可靠監察 · 安全守門

未有事，已經知道

  • NVMe 壽命預測 + critical warning（呢平台有已知 No-NVMe 故障）
  • container OOM / restart loop → 即時警報
  • kernel / OOM / NVRM 日誌 markers（24h 有事冇事一眼睇）
  • 睇 log：/logs 攞 vLLM / kernel / 服務 / container 日誌（限行數 + auth）
  • security audit：open ports、failed SSH、異常 process/container

安全

  • API read-only 預設 ＋ Token / API-Key
  • 站與站用 mTLS 或 WireGuard 加密
  • vLLM 控制（可選）受控 ＋ 唔 auto-wake
即時告警

未出事，已經話你知

GPU > 96°C / SM clock 崩過熱降頻 / USB-C PD 卡死CRIT
Disk TTF < 6h磁碟就快快滿WARN
KV cache 飽和 ＋ 排隊 ＋ preempt模型唔夠位，要加 nodeWARN
RDMA link down / 擁塞升fabric 出問題CRIT
vLLM engine dead (health≠200)推理死機，即刻喊CRIT
架構

分層清晰，通訊安全

L4 Consumer：你部機 / Prometheus / Grafana
L3 API：gateway — /health · /cluster.json · /metrics · /logs · /control
L2 Exporter：每部 DGX 一個 :9101（一等公民）
L1 Collectors：hardware · system · network · services · vllm（並行）
L0 數據源：nvidia-smi / proc / sys / docker / vLLM / RDMA

通訊安全

  • 出外：token ＋ read-only ＋ TLS
  • 站與站：mTLS / WireGuard 加密
  • /logs 敏感 → auth；/control 受控
部署

幾分鐘上線、遷移就把炮

  • 每節點 venv ＋ systemd（原裝 DGX OS，ARM64 wheels 齊）
  • 冪等 install.sh：--role --node-id --mgmt-ip，加機 3 步
  • hardened systemd unit（NoNewPrivileges / ProtectSystem …）
  • 可選 Docker 路徑
  • 升級／回滾：install.sh --update／--uninstall

部署三句

  • ① clone ＋ install.sh
  • ② 定 token / 角色
  • ③ 起 service — 完成
整合

唔係孤島

  • Prometheus / Grafana：內建 /metrics 直接被撈 → dashboard + alert
  • Webhook / Telegram（可選）：出事即 push
  • SQLite 歷史 / ring buffer：即時 ＋ 回溯（可配 Prometheus TSDB 長史）
  • vLLM 控制（可選）：abort-by-id、pause/resume — 受控 ＋ 唔干預

擴到大型集群？

N 前預設單 gateway；N 大到可 federation / 多級 gateway
