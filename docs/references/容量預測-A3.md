# DGX status API — Capacity Prediction (A3): Implementation-Ready Research

Target: 2..N-node DGX Spark (GB10) status/performance API. Goal = warn "add a node / free space"
before failure. Two signals: (1) disk time-to-full (TTF), (2) KV-cache / GPU-memory headroom trend.
Research only; everything below is reusable / implementation-ready.

Key platform facts this builds on (from `dgx-spark-monitoring` skill):
- UMA: 128 GB shared CPU+GPU. **`nvidia-smi` memory fields are N/A.** Correct memory = `/proc/meminfo`
  `MemAvailable`/`MemTotal`, or node_exporter `node_memory_MemAvailable_bytes`.
- vLLM KV cache: `vllm:kv_cache_usage_perc` (Gauge, 0–1). (≤0.11.x legacy name `vllm:gpu_cache_usage_perc`.)
- Disk: node_exporter `node_filesystem_avail_bytes` / `node_filesystem_free_bytes` (or df/statvfs).
- Retention: SQLite WAL `samples(node,ts,metric,value,meta)` 30d; real long history = Prometheus TSDB.
  → Prediction should run against Prometheus (applies naturally to the API's `/history` + `/metrics`).

## 1. DISK TIME-TO-FULL (TTF)

### 1a. Recommended method: `predict_linear()` (Prometheus-native, zero hand-rolling)

Prometheus already ships the exact function for this. Official (v3.x docs, "Query functions"):

> `predict_linear(v range-vector, t scalar)` predicts the value of (a) time series `t` seconds from
> now, based on range vector `v`, **using simple linear regression**. The range vector must have at
> least two float samples... Should only be used with gauges. Returns NaN if ±Inf in the range.
> `predicted_value = value_at_evaluation_time + slope * time`

**Core formula (canonical, from Brian Brazil / Robust Perception & Grafana docs):**
```promql
# TTF < horizon  =>  disk fills before "now + horizon"
predict_linear(node_filesystem_free_bytes{mountpoint="/", instance="node-a"}[1h], 4*3600) < 0
```
`< 0` on *free* bytes = projected free space goes negative in the horizon → disk full before that time.

**Alternate direct "hours-to-full" expression** (compute, don't threshold against 0):
```promql
# disk_ttf_hours - projected hours until the disk is exhausted, given recent slope
(
  predict_linear(node_filesystem_avail_bytes{...}[6h], 0)
  / clamp_min(
      deriv(node_filesystem_avail_bytes{...}[6h]) * 3600 * -1,   # positive free-bytes/hour
      0.001
    )
)
```
Simpler / more robust if you want a single number to expose as `disk_ttf_hours`:
`TTF = available / growth_rate`, where `growth_rate = -slope(available)`. Two robust ways to get slope:
- **Rate-extrapolation**: `node_time_seconds - (node_filesystem_avail_bytes / -deriv(avail[window]))`.
- **`predict_linear` as the slope source** is what the metric below does.

### 1b. Recommended metric + alert (concrete)

Expose one gauge **`disk_ttf_hours`** (projected hours before full) per node+mount. From Prometheus,
either record a recording rule or compute in the API over the Prom range query:

```promql
# recording rule: projected hours to full
disk:node_filesystem_ttf_hours{mountpoint=~"/|/data.*"}
  = (1 - predict_linear(node_filesystem_avail_bytes[6h], 0) / node_filesystem_size_bytes)
    / clamp_min(-deriv(node_filesystem_avail_bytes[6h]) / node_filesystem_size_bytes, 0)
```
Then two alert thresholds (align with your existing disk>85% style conventions):
```promql
- alert: DiskWillFillSoon
  expr: predict_linear(node_filesystem_avail_bytes{mountpoint=~"/|/data.*"}[6h], 4*3600) < 0
  for: 5m            # debounce spikes
  labels: { severity: warn }
- alert: DiskWillFillNow
  expr: predict_linear(node_filesystem_avail_bytes{mountpoint=~"/|/data.*"}[6h], 6*3600) < 0
  for: 5m
  labels: { severity: crit }
```
**Thresholds to recommend (add to API alert config):**
| alert | horizon | meaning |
|---|---|---|
| `DiskWillFillSoon` | warn, H=4h | TTF < 4h → free space now / stop write-heavy job |
| `DiskWillFillNow` | crit, H=6h | projected full within ~6h → page / urgent |
| (optional) capacity-days warn | TTF < 24h, eval 12h | slow-growth planning signal: "add a node / prune models" |

Grafana's official guidance for the slow daily-growth case: evaluate a 14d window on a 1h subquery,
forecast +7d, alert when predicted usage >85%:
```promql
predict_linear(
  max by (persistentvolumeclaim)(100*(1 - kubelet_volume_stats_available_bytes / kubelet_volume_stats_capacity_bytes))[14d:1h],
  7*24*3600
) > 85
```

### 1c. Window size / sample count / spike & seasonal filtering

- **Window (`[W]`)**: match to the growth you care about, not the scrape tick. For DGX NVMe w/ model
  weight dumps, **6–24h** is a sane default for "am I about to fill". Grafana uses 14d for config-drift
  capacity planning. Don't use a 1-min window (a single `predict_linear` from a 1-min spike is noise).
- **Sample count**: `predict_linear` needs **≥2 float samples**; realistically you want **≥1 sample per
  5× the resolution** so `[6h]` with 15s scrape ≈ 1440 points — plenty. If a range has one stuck value
  (agg lifecycle/cron pause), the fit is a flat line → slope ≈ 0 → `clamp_min(...,0.001)` prevents div-by-0.
- **Spike / one-off event filtering (avoid predicting from a 1-min spike):**
  - Debounce with `for: 5m` (Brazil's canonical pattern).
  - **Trend, not level:** `predict_linear(..., H) < 0` is already trend-based (slope), so a 1-min blip
    of availability won't flip a 6h-linear-fit; it's the level thresholds that get spiked. For the
    TTF metric use the slope, never `avail_bytes < X` alone.
  - **Min-sample guard:**
    ```promql
    deriv(node_filesystem_avail_bytes[6h]) != 0
    and on() (count_over_time(node_filesystem_avail_bytes[6h]) > 120)
    ```
  - **Stale handling:** if the mount is read-only/no writes for a long time, slope→0 and TTF→∞; clamp
    and surface `disk_ttf_hours == 0` when flat (means "no trend / data insufficient"), don't alert.
- **Seasonality:** disk growth on DGX is mostly monotone (weight/model dumps, logs). `predict_linear`
  is the right tool. If you ever track *network/CPU* with daily seasonality, don't use linear forecast —
  see Grafana ML section (3). Filter out the model-cache/checkpoint mounts you don't count
  (`mountpoint=~"...!(?i)(docker|containerd|/proc|/sys)"`).

## 2. KV-CACHE / GPU-MEMORY HEADROOM TREND

### 2a. UMA reality (GB10)
On GB10 there is **no separate GPU framebuffer** to watch. "GPU memory headroom" == **system RAM
headroom** from `/proc/meminfo MemAvailable` (node_exporter `node_memory_MemAvailable_bytes`) minus
what vLLM holds. vLLM's KV cache is allocated as **HugePages** in that same 128 GB UMA pool, so the
two are on literally the same budget. Therefore:
- **KV-cache headroom** = `1 - vllm:kv_cache_usage_perc` (0–1). It's a fraction of the *allocated*
  KV blocks, not of total RAM. It's the direct "will the next request preempt" signal.
- **System/UMA headroom** = `node_memory_MemAvailable_bytes` (absolute bytes) OR the inverse
  `1 - node_memory_MemAvailable_bytes/node_memory_MemTotal_bytes`.

### 2b. Surface headroom as metrics (add to API)
```promql
# 0..1, higher = headroom left for KV (relative to vLLM's own KV allocation)
vllm:kv_cache_headroom = 1 - vllm:kv_cache_usage_perc            # gauge
# absolute UMA headroom (bytes) - the real shared-total ceiling
node:uma_mem_available_bytes = node_memory_MemAvailable_bytes    # gauge
# UMA pressure (0..1) - when vLLM preloads weights this is the one to watch
node:uma_mem_used_ratio = 1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
```

### 2c. Trend detection (up / saturation)
Two complementary approaches:

**(A) Trend toward 1.0 (saturation) with `predict_linear`** — alert on the forecast, not the level:
```promql
# KV cache projected to saturate (usage -> 1.0) within the horizon
- alert: KVCacheWillSaturate
  expr: predict_linear(vllm:kv_cache_usage_perc[15m], 1800) > 0.95
  for: 5m
  labels: { severity: warn }
# UMA (system RAM) projected exhaustion within the horizon
- alert: UMAHeadroomExhausting
  expr: predict_linear(node_memory_MemAvailable_bytes[30m], 6*3600) < 0
  for: 5m
  labels: { severity: warn }
```
**Rate/trend (slope) metrics** to expose for the API trend field + dashboard:
```promql
# bytes/hour change in headroom (negative = filling)
node:uma_headroom_slope_1h = deriv(node_memory_MemAvailable_bytes[1h]) * 3600
# KV usage drift per hour (>=0.02/h meaningfully approaching saturation)
vllm:kv_usage_drift_1h = (vllm:kv_cache_usage_perc - vllm:kv_cache_usage_perc offset 1h)
```

**(B) The important vLLM caveat — do NOT alert on a raw threshold alone.** From akrisanov's
production vLLM monitoring guide (and vLLM maintainers): high `kv_cache_usage_perc` is **normal and
healthy** under continuous batching — the scheduler fills the cache by design and preempts rather
than stalls. A universal "80% / 95%" KV alert produces noise. The *real* saturation signal is the
**combination**: KV near its normal ceiling **+** rising queue/backlog (`num_requests_waiting`,
`sustained queue_time`) **+** rising preemptions (`rate(vllm:num_preemptions[5m])`) **+** worsening
latency (TTFT/ITL, `e2e_request_latency`). Recommended alert:
```promql
- alert: KVCachePressure
  expr: vllm:kv_cache_usage_perc > 0.95
         and (rate(vllm:num_preemptions_total[5m]) > 0)
         and (vllm:num_requests_waiting > 0)
  for: 5m
  labels: { severity: warn }
```
**Note:** `kv_cache_usage_perc` reaching exactly 1.0 does **not** mean OOM — it means zero spare KV
blocks → every new request risks preemption/recompute (capacity to *add a node* is precisely the remedy).

### 2d. GB10-specific UMA gotchas
- `predict_linear(node_memory_MemAvailable_bytes[30m], 6h) < 0`: MemAvailable moves a lot with page
  cache (Linux reclaims it under pressure) → use ≥30m–1h window and `for: 5m`; transient page-cache
  ops (weights load, model swap) will otherwise false-positive.
- vLLM model **weights load / engine sleep (weights_offloaded / discard_all)** temporarily drop
  MemAvailable and can flip a short-window KV/RAM forecast → gate forecasts, or use a longer window.
- Always pair with the existing throttle/health signals, not alone.

## 3. OFF-THE-SHELF vs HAND-ROLLED

| Approach | What it is | Use for | Effort | Notes / source |
|---|---|---|---|---|
| **`predict_linear()` PromQL** | linear regression + extrapolation | disk TTF, KV/RAM trend | **0** | ✅ recommended; ships in Prometheus; Grafana officially documents alerting on it (`docs/grafana/latest/alerting/guides/alerting-on-forecasts/`) |
| **Grafana panel: forecast projection** | query `predict_linear(.., ..)` twice (past & +H), set time-range `To = now+H`; add `offset`/math via **Add field from calculation** (binary/unary) + **threshold transform** | dashboard "projected free space" overlay | low | Grafana transform docs (Add field from calculation, Threshold, Mathematical). No install. |
| **Grafana alert on forecast** (`predict_linear` w/ subquery `[14d:1h]`) | eval every 12h, fire when predicted usage > X | slow capacity planning | low | official docs example (Postgres PVC) |
| **Grafana Cloud Machine Learning forecasting** (Prophet-style) | forecast *series* + `yhat`/`yhat_upper`/`yhat_lower` bounds + `anomalous` metric; alerts on `:predicted{ml_forecast="yhat_upper"}` or `:anomalous` | signals with **daily/weekly seasonality** (traffic, not monotone disk) | med (cloud) | official "Alerting on forecasts"; `grafanacloud-ml-metrics` DS. **Overkill for DGX** (monotone growth), mention only. |
| **`deriv()` rate-extrapolation** (`TTF=avail/rate`) | slope * rate | hand-rolled TTF where no Prom TSDB (pure SQLite path) | med | ServerFault "calculating days until disk is full"; use `clamp_min` to avoid div-by-0 |
| **Hand-rolled numpy/OLS in the API** | fit line over `samples` table | if you must predict *inside* the API without Prometheus evaluation | med | 5-step OLS: mean(x),mean(y), Sxx,Sxy → slope, intercept; predict y at horizon; extrapolate to `y=0`. ~40 lines. |

**Recommendation:** Use **Prometheus `predict_linear()`** as the primary engine (it is both the
off-the-shelf and the correct tool for monotone disk/RAM growth on DGX). Expose derived gauges
`disk_ttf_hours`, `vllm:kv_cache_headroom`, `node:uma_mem_used_ratio` from the API so clients don't
recompute. Only hand-roll OLS if you explicitly want SQLite-only prediction with no Prometheus.

## 4. EFFORT + GB10 GOTCHAS SUMMARY

### Effort
- **Disk TTF:** trivially implemented. Prometheus already stores the series; a recording rule + 2
  alert rules is the whole change. ~0.5 day incl. dashboard panel.
- **KV/RAM headroom trend:** also small (~0.5 day). Add `kv_cache_usage_perc` to the parsed vLLM set
  (already scraping `/metrics`; see `vllm-metrics-parsing` ref for name mapping), MemAvailable already
  collected. Add 3 gauges + 2 trend alerts.
- **Grafana dashboard:** 1 extra panel each (threshold/calculate-field transforms). Low.

### Gotchas (GB10 / vLLM)
1. **UMA = one budget.** "GPU headroom" and system RAM headroom are the *same bytes*. Watch
   `node_memory_MemAvailable_bytes`, never `nvidia-smi` memory (N/A on GB10).
2. **vLLM holds KV in HugePages of that same pool** — a big model load and KV growth both eat
   MemAvailable; don't double-over-interpret two metrics on the same budget.
3. **Don't alert KV on a raw % threshold**; combine with queue/preemption/latency (prod vLLM guidance).
4. `predict_linear` = **gauges only**, needs **≥2 samples**, NaN if ±Inf in range; debounce with
   `for: 5m`; use ≥6h (disk) / ≥15–30m (RAM) windows so one short spike doesn't flip the forecast.
5. **`deriv` zero-growth** → clamp denominator; treat flat slope as "no trend" (TTF=∞), don't page.
6. **vLLM engine sleep / weight offload** creates MemAvailable dips → gate forecasts or lengthen window.
7. vLLM metric-name version drift: `kv_cache_usage_perc` (0.20/0.22/NGC 26.x) vs `gpu_cache_usage_perc` (≤0.11.x) — probe names at first scrape (per skill ref).
