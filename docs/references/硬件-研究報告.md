# DGX Spark (GB10) 硬體狀態讀取方式研究報告

**平台**: NVIDIA DGX Spark, GB10 Grace Blackwell Superchip, DGX OS (Ubuntu 24.04) ARM64。
**核心特性（影響所有監控方式）**: 128GB **統一記憶體 (UMA)**——CPU 與 GPU 共用同一 LPDDR5x 記憶體池，無獨立 VRAM framebuffer。
來源: https://docs.nvidia.com/dgx/dgx-spark/system-overview.html , https://docs.nvidia.com/dgx/dgx-spark/known-issues.html

**最重要的總結性結論（請全讀再實作）**:
- nvidia-smi 的 **memory.used/memory.total/utilization.memory 全部不支援**（回報 `Not Supported` / `N/A` / `0`）。
- NVIDIA **官方對外聲明「無計畫支援 DCGM on Spark」**，所以 dcgm-exporter / dcgmi DCGM 系列**不可用**。
- **GPU 記憶體真實用量只能看系統層級 RAM**（`free -h` / `/proc/meminfo`），因 GPU 與 CPU 共用同一個記憶體池。
- 可靠且有實測實證的 GPU 欄位僅剩: `temperature.gpu`、`utilization.gpu`、`power.draw`、`clocks.*`、`name`、`driver_version` 等少數。
- 唯一被 NVIDIA 官方支援的整合監控介面是 **DGX Dashboard**（本機 web UI）。

## 1. nvidia-smi / NVML

**KEY FACT (已驗證)**: DGX Spark 為 UMA，無專屬 framebuffer 記憶體，故 `nvidia-smi` 主表顯示 `Memory-Usage: Not Supported`。
- 官方 Known Issues 原文: "On iGPU platforms, nvidia-smi will display 'Memory-Usage: Not Supported'... this is expected because iGPUs do not have dedicated framebuffer memory."
  來源: https://docs.nvidia.com/dgx/dgx-spark/known-issues.html
- NVIDIA 支援文: "When I run Spark's nvidia-smi to see the memory usage it says 'Not Supported'. This is expected behavior. The DGX Spark has a unified memory..."  https://nvidia.custhelp.com/app/answers/detail/a_id/5775/
- 真實 pynvml 輸出實證 [Beszel 監控文]:
  ```
  GPU: NVIDIA GB10
  Temperature: 37°C
  GPU Util: 0%
  Power: 4.487W
  Memory query failed: Not Supported
  ```
  來源: https://forums.developer.nvidia.com/t/monitoring-nvidia-jetson-thor-and-dgx-spark-with-beszel/364762
- NVML `nvmlDeviceGetMemoryInfo()` 回傳 `NVML_ERROR_NOT_SUPPORTED`。
  來源: https://forums.developer.nvidia.com/t/dcgm-exporter-missing-process-level-attribution-for-gpu-time-slicing-on-blackwell-gb10/363037

### 指令
```
nvidia-smi --query-gpu=FIELD,... --format=csv,noheader,nounits
```

### 各 query-gpu 欄位在 GB10 上是否可信 (依官方 Known Issues + 社群實測)

| 欄位 | 在 DGX Spark 狀態 | 說明 |
|---|---|---|
| `name` | ✅ 正常 | 回報 "NVIDIA GB10" |
| `driver_version` | ✅ 正常 | 如 580.95 |
| `pstate` | ✅ 正常 | P0..P8 效能狀態 |
| `persistence_mode` | ✅ 正常 | 持久模式 |
| `utilization.gpu` | ✅ 正常 | GPU SM 利用率 % |
| `utilization.memory` | ⚠️ **回報 0** | UMA 無獨立記憶體控制器測量，**不可信** |
| `temperature.gpu` | ✅ 正常 | GPU 核心溫度 °C |
| `temperature.memory` | ⚠️ 通常 N/A | UMA 無離散 memory 感測器 |
| `power.draw` | ✅ 正常 | GPU 功耗 W（實測 4.5W idle） |
| `power.limit` | ✅ 正常 | 功耗上限 |
| `clocks.sm` / `clocks.graphics` | ✅ 正常 | SM 頻率，正常應 ~2400MHz，被 throttled 會 <850MHz |
| `clocks.mem` | ⚠️ 可能 N/A | UMA 無獨立 memory clock |
| `pcie.link.gen` | ⚠️ 可能 N/A | iGPU 無 PCIe link |
| `compute_mode` | ✅ 正常 | |
| `fan.speed` | ⚠️ 常 N/A | 風扇由 EC 控制，nvidia-smi 常不報（見社群風扇故障文） |
| `memory.used` / `memory.total` | ❌ **[N/A]** | **不可用**——用系統 RAM 代替 |
| `memory.free` / `clocks.max.*` 等 | ❌ N/A | 同上 |

- query-gpu memory 實測輸出: `[N/A], [N/A], 0` (used,total,util).
  來源: https://github.com/mostlygeek/llama-swap/issues/782

### nvidia-smi dmon / pmon
- `nvidia-smi dmon` 與 `nvidia-smi pmon` **可用，但 memory 利用率在 GB10 上報 0**（因 UMA）。
  來源: https://github.com/mostlygeek/llama-swap/issues/782

### 有用的替代: per-process GPU 記憶體
- `nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory` 反而**有回傳有值**（每人 process 的 resident unified memory，例如 19135MB）。這是唯一 nvidia-smi 內可拿到的「GPU 記憶體」近似值。
  來源: https://github.com/mostlygeek/llama-swap/issues/782

## 2. tegrastats

**狀態**: ⚠️ **DGX Spark 上「預設不存在」**——tegrastats 是 JetPack/Jetson 專用工具，**DGX OS (Ubuntu) 不含它**；DGX Spark 用 nvidia-smi 取代。
- 實證: Beszel 監控文中「Jetson Thor 內建 tegrastats，DGX Spark 用 nvidia-smi」。來源: https://forums.developer.nvidia.com/t/monitoring-nvidia-jetson-thor-and-dgx-spark-with-beszel/364762
- tegrastats 本質（在 Jetson/Grace 上）:
  - 路徑 `/usr/bin/tegrastats`（Jetson）或 `/usr/local/bin/tegrastats`（部分套件）。
  - 每秒印刷一行時間戳+CPU 各核負載、GPU 利用率、RAM、power、thermal、電壓。
  - 範例格式 (Jetson host): `10-30-2024 17:57:06 ... CPU [x%@...] GR3D_FREQ % EMC_FREQ ... RAM ...` 來源: https://forums.developer.nvidia.com/t/tegrastats-missing-information-when-run-inside-a-container/311539
  - Thor 上 tegrastats 無法顯示 GPU 利用率（標註 "pmon is currently not supported on Thor"）——新版 RJN(Grace/Blackwell) 上 nvgpu 利用率取用受限。來源: https://forums.developer.nvidia.com/t/tegrastats-cant-display-gpu-utilization/351797
- **結論**: 在 **DGX OS on DGX Spark 上不要依賴 tegrastats**；需自行確認（`which tegrastats`），若有（部分使用者手動裝回）才可用，否則用 nvidia-smi。

## 3. NVIDIA DCGM + dcgm-exporter + dcgmi

**狀態**: ❌ **在 GB10 (DGX Spark) 上不支援**。這是確認過的最重大限制。
- NVIDIA 官方: "There are **no plans to support DCGM on Spark**."
  來源: https://forums.developer.nvidia.com/t/mps-support-and-telemetry-on-grace-blackwell-gb10-with-unified-memory/363137
- 官方回覆 dcgm 議題: "Unfortunately, **DCGM is not supported on GB10** so I cannot say what configuration will work."
  來源: https://forums.developer.nvidia.com/t/dcgm-exporter-missing-process-level-attribution-for-gpu-time-slicing-on-blackwell-gb10/363037
- dcgm-exporter 在 Spark 上「exporter 在跑但儀表板全空」: 靜默失敗。
  來源: https://agmind.ai/reports/dgx-spark-gpu-monitoring/
- 即使硬跑，`DCGM_FI_DEV_FB_USED/FREE/...` 等 framebuffer、VRAM、NVLINK、ECC、XID 計數在 UMA iGPU 上多數無實值；dcgm-exporter 給出「mirrored」利用率、VRAM 報 0MB/N/A。
  來源: https://forums.developer.nvidia.com/t/mps-support-and-telemetry-on-grace-blackwell-gb10-with-unified-memory/363137

**結論**: `dcgmi dmon` 在 DGX Spark 上**不可用**。改用官方 Dashboard 或解析 nvidia-smi（見第 1/10 節）。

## 4. jetson-stats / jtop (rbonghi/jetson_stats)

**狀態**: ⚠️ **可用但意義有限**。jtop 依賴 tegrastats 與 Jetson 專用節點（`/usr/sbin/tegrastats`、`/usr/bin/tegrastats` TEGRASTATS 路徑掃描），在 **非 Jetson 平台（含 DGX OS）常顯示 "Tegrastats is not available on this board"**，故 GPU 分頁多空轉。
- 安裝指令 (pip): `sudo pip3 install jetson-stats`（Ubuntu 需加 `--break-system-packages`）; 來源: https://github.com/rbonghi/jetson_stats
- 依賴 tegrastats 找不到的已知 issue: https://github.com/rbonghi/jetson_stats/issues/38
- JP6 上 services 啟動失敗 issue: https://github.com/rbonghi/jetson_stats/issues/484

**結論**: 不建議作為 DGX Spark 的正式監控；可在臂機上裝 `sensors`/自寫解析替代。

## 5. 系統層 CPU / RAM（✅ 皆可用，這是 UMA 記憶體的唯一正確來源）

因為 GPU 記憶體 = 系統記憶體，**記憶體監控一律走 OS 層**:
```
free -h                       # Mem / Swap 用量與總量（128GB）
cat /proc/meminfo             # MemAvailable / SwapFree / HugePages （官方推薦做法）
cat /proc/stat                # CPU 數與負載
lscpu                         # 架構(Arm aarch64)、核心數(20-core)、型號
uname -a                      # kernel, 架構（aarch64）
cat /etc/os-release           # DGX OS = Ubuntu 24.04
uptime                        # 併出 loadavg
```
- **官方 128GB 算可用性指引**: 用 `/proc/meminfo` 的 `MemAvailable + SwapFree`（HugePages 例外）估算可分配 device memory，因為 CPU 可把 DRAM 頁 swap 掉。官方甚至給出解析 `/proc/meminfo` 的 C sample。來源: https://docs.nvidia.com/dgx/dgx-spark/known-issues.html
- Bugtip: `cudaMemGetInfo()` 回報偏小（不計可 reclaim 的 swap），勿直接信。NVIDIA Knowledged: https://nvidia.custhelp.com/app/answers/detail/a_id/5728/
- 20-core ARM64 CPU (10×Cortex-X925 P + 10×Cortex-A725 E)。來源: https://docs.nvidia.com/dgx/dgx-spark/system-overview.html

## 6. 散熱 / 溫度

```
cat /sys/class/thermal/thermal_zone*/temp   # 各 thermal zone 溫度(毫°C)
sensors                                       # lm-sensors 讀 hwmon
```
- ✅ **可用**。Linux hwmon 驅動 (SPBM) 暴露 8 個 thermal zone: `tj_max`, `cpu_e_clu0/1`, `cpu_p_clu0/1`, `gpu`, `soc`（+更多）。
  來源: https://github.com/antheas/spark_hwmon
- `sensors`/hwmon 亦靠此驅動。此驅動也回報完整功率能量通道（見第 7 節）。
- DGX Spark 有已知 **EC/韌體更新後 96–97°C 節流**問題討論，溫度監控對健康判斷重要。
  來源: https://forums.developer.nvidia.com/t/dgx-spark-gb10-thermal-throttling-after-ec-uefi-updates-acpi-zones-96-97c-fans-not-ramping/377044
- 規格理想操作溫度 5–30°C。來源: https://docs.nvidia.com/dgx/dgx-spark/hardware.html

## 7. 功率 / 能量

- **nvidia-smi `power.draw`**: ✅ 可用（GPU 部分，idle ~4.5W）；`power.limit` 可用。來源: https://forums.developer.nvidia.com/t/monitoring-nvidia-jetson-thor-and-dgx-spark-with-beszel/364762
- **整機功率**: `/sys/class/hwmon`（透過 SPBM hwmon 驅動，需 `antheas/spark_hwmon`）。驅動讀 SPBM shared memory，暴露 14 個 power channel (`sys_total`, `soc_pkg`, `cpu_gpu`, `cpu_p`, `cpu_e`, `vcore`, `dc_input`, `gpu`, `prereg`, `dla`, `pl1/pl2/syspl1/syspl2`) + 4 個能量累計器 (`pkg`, `cpu_e`, `cpu_p`, `gpu`)。
  - 峰值: 系統 240W，GPU+CPU 140W (NVIDIA forum 確認)。
  來源: https://github.com/antheas/spark_hwmon , https://forums.developer.nvidia.com/t/dgx-spark-observed-behaviour-power-draw-performance-discrepancy/349307
- ⚠️ **NVIDIA 官方聲明「無方法監控 CPU 功率」**(on DGX Spark)。spark_hwmon 是社群 hack。來源: https://forums.developer.nvidia.com/t/help-needed-how-to-enable-grace-cpu-power-telemetry-on-dgx-spark-gb10/360631 (經 spark_hwmon README 引用)
- **AC/電池**: 無（桌面桌上型，僅 AC）。
- 能量累計器比即時功率更穩定（firmware 100ms PID 造成即時值振盪）。同上 spark_hwmon source。

## 8. NVML unified-memory shim（CINOAdam/nvml-unified-shim）

**目的**: 攔截 NVML 呼叫（`LD_PRELOAD`），當 `nvmlDeviceGetMemoryInfo()` 回 `NVML_ERROR_NOT_SUPPORTED` 時，退回 CUDA runtime + `/proc/meminfo` 提供 unified memory 用量給那些假設有 VRAM 的應用（Modular MAX Engine, nvtop, TensorRT tools 等）。
- 用法: `LD_PRELOAD=./libnvml-unified.so <app>`，drop-in，免改程式碼。
- 已於 MAX Engine 與 nvtop on GB10 測試。
  來源: https://github.com/CINOAdam/nvml-unified-shim (README), https://forums.developer.nvidia.com/t/mps-support-and-telemetry-on-grace-blackwell-gb10-with-unified-memory/363137

**對我們的 API 意義**: 這是「讓現有 GPU 監控工具別死掉」的 shim，不是官方數值來源；我們自己的 API 直接 parse nvidia-smi/`/proc/meminfo` 即可，不需要它。

## 9. Clock / boost / XID / ECC（健康）

### Clocks (✅ 可用，健康判斷重要)
```
nvidia-smi --query-gpu=clocks.sm,clocks.graphics,clocks_mem --format=csv,noheader
```
- `clocks.sm`/`clocks.graphics` **可靠**。正常滿載 ~2400MHz；被 power-throttle 時 <850MHz（即使 P0 狀態）。
- 有已知「GPU 卡在 P0 但降頻 <850MHz」的 power-throttle 缺陷（可疑係 USB PD 供電問題），`hoesing/spark-gpu-throttle-check` 用 cuBLAS 載入並監看時脈判 throttling。
  來源: https://github.com/hoesing/spark-gpu-throttle-check , https://forums.servethehome.com/index.php?threads/testing-power-limit-on-gb10-spark-never-goes-over-35-watts.55860/
- 另一社群回報「GPU 卡在 15W/650MHz loop，T Limit 50°C」的節流實例。來源: https://forums.developer.nvidia.com/t/dgx-spark-grace-blackwell-gb10-performance-drop-gpu-trapped-in-15w-650mhz-loop-with-50-c-artificial-t-limit-temp/370304

### XID / ECC
- ⚠️ **N/A / 不可用**。XID 錯誤、ECC 計數、ECC 記憶體皆依賴 framebuffer/記憶體控制器細粒計數；UMA iGPU 上 DCGM(ECC/XID) 路徑已確認不支援（見第 3 節）。不要依賴 DCGM 的 `DCGM_FI_DEV_XID_ERRORS`、`DCGM_FI_DEV_ECC_*` 於 GB10。
- 系統層「GPU 有無 crash/reboot 跡象」仍可看 `nvidia-smi` 是否回報正常值 + `dmesg`。

## ✅ 建議的最小硬體指標集合（2× DGX Spark HTTP status API）
每節點（每台 DGX Spark）收集:

**GPU (nvidia-smi --query-gpu=... )**
1. `name` — 型號 (NVIDIA GB10)
2. `driver_version` — 驅動
3. `pstate` — 效能狀態
4. `utilization.gpu` — SM 利用率 %
5. `temperature.gpu` — °C
6. `power.draw` — GPU 功耗 W
7. `power.limit` — 功耗上限
8. `clocks.sm` / `clocks.graphics` — 頻率（throttle 偵測；<850MHz=P0節流）
9. `clocks.max.sm` — 最大頻率參考
10. `--query-compute-apps=used_memory` — 每 process 的 GPU(RAM) resident 用量（唯一 NVML 記憶體值）

**系統記憶體（UMA = 真正 GPU 記憶體池）**
11. `MemTotal`, `MemAvailable`, `SwapFree`（`/proc/meminfo`）
12. `free -h` 維持的 used+total

**CPU / 系統**
13. 每 core 使用率（`/proc/stat` 計算）— 20 core
14. `loadavg` / `uptime`
15. `MemAvailable` 趨勢（記憶體健康）

**功率 / 能量（系統）**
16. `sys_total` power + `gpu` power（若安裝 spark_hwmon 驅動 → `sensors`/hwmon sysfs); 無則退而求其次 nvidia-smi power.draw

**溫度（熱）**
17. `tj_max` / `gpu` / `soc` zone（`/sys/class/thermal/thermal_zone*/temp` 或 `sensors`）— 監看是否接近 96–97°C 節流線

**健康/狀態**
18. 感知器存活 flag（`nvidia-smi`/解析程序的成功/時間戳 + 對解析器本身的 staleness 警報——避免「儀表板全空」陷阱，見 agmind 報告)
