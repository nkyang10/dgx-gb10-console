# 狀態-09 · 熱控制 / 降頻（Thermal Control & Downclock）觀測矩陣

> collector：`collectors/hardware.py`（GPU）＋ `collectors/system.py`（thermal/cpu-freq）
> 優先級：⭐必備（GPU 熱降頻係 DGX 最常見嘅效能隱形殺手）
> 核心問題：**「點睇到 DGX 因為過熱而降頻？」**——答案係**唔可以淨睇溫度或少時脈一件事**，要同時對著成個矩陣。

---

## 0. 熱降頻（thermal downclock）係咩

GPU/CPU 過熱 → 溫度保護機制**主動降低時脈**（要做返低功耗）→ 效能下降但唔會 crash。要 detect 就要同時睇：**溫度 + 時脈 + throttle reason + 負載**——四樣夾埋先判到。

---

## 1. 觀測矩陣（MATRIX）—— 同時對返呢幾個 signal

| Signal | 點攞 | 單位 | 健康閾值 | 熱降頻跡象 |
|---|---|---|---|---|
| **溫度 GPU** | `nvidia-smi --query-gpu=temperature.gpu` | °C | <80（warn）/ <92 | 逼近 96–97°C 節流線 ⚠️ |
| **溫度 SOC/tj_max** | `/sys/class/thermal/thermal_zone*/temp`（spark_hwmon zones：`tj_max`/`soc`/`gpu`/`cpu_e_clu`/`cpu_p_clu`） | °C | — | 任一接近節流線 |
| **SM 時脈（實際）** | `clocks.current.sm` | MHz | ≈max（滿載 ~2400MHz） | **跌到 <850MHz**＝顯著降頻 |
| **SM max 時脈** | `clocks.max.sm` | MHz | — | 對照用 |
| **clock 比例** | `clocks.current.sm / clocks.max.sm` | ratio | ≥0.8 | **<0.45＝卡死/節流** |
| **throttle reason** | `clocks_throttle_reasons.active`（**underscore**，driver 580+）＋細分 | bitmask | 0 | 非 0＝有原因 throttling |
| **功率** | `power.draw` vs `power.limit` | W | draw≤limit | draw>limit cap＝power 節流（vs thermal） |
| **CPU 頻率** | `scaling_cur_freq` vs `scaling_max_freq` | MHz | — | CPU 都降頻（熱或 power cap） |
| **負載 util** | `utilization.gpu` | % | — | 判「真降頻」vs「idle 降頻」：util 高先算節流 |

---

## 2. 判讀規則（Decision Table）—— 到底係咪「熱降頻」？

| 情形 | temp | clock% | throttle reason | util | 判定 |
|---|---|---|---|---|---|
| 正常滿載 | 正常 | ≥0.8 | 無 | 高 | ✅ 正常 |
| **熱降頻** | **近 96–97 / >80** | **低** | **`hw_thermal_slowdown`/`sw_thermal_slowdown`** | 中高 | 🔴 **過熱降頻**（要散熱/降載） |
| **功率節流** | 正常 | 低 | **`sw_power_cap`/`hw_power_brake_slowdown`** | 高 | 🟠 power cap（限功耗） |
| **卡死低時脈**（GB10 特殊） | 正常 | **<45%** | 「無」any throttle reason | ≥50% | 🔴 USB-C PD/power 故障（sparktop 45% 規則） |
| idle 低時脈（正常） | normal | 低 | 可能 `idle` | ~0 | ✅ 正常節能 |

> ⚠️ **關鍵**：**「低時脈但 throttle reason 無」+ util 高 + power 正常** = GB10 特有嘅卡死 bug（USB-C PD 供電問題），唔係熱！所以 throttle reason 一定要睇——唔好淨靠時脈判斷。
> ⚠️ **熱 vs 功率分唔分到**：睇 throttle reason 邊隻 bit set：
> - `hw_thermal_slowdown` / `sw_thermal_slowdown` → **熱**（溫度引致）
> - `sw_power_cap` / `hw_power_brake_slowdown` → **功率上限**（唔係熱）

## 3. nvidia-smi exact query

```bash
nvidia-smi --query-gpu=temperature.gpu,clocks.current.sm,clocks.max.sm,clocks_throttle_reasons.active,clocks_throttle_reasons.hw_thermal_slowdown,clocks_throttle_reasons.sw_thermal_slowdown,clocks_throttle_reasons.sw_power_cap,clocks_throttle_reasons.hw_power_brake_slowdown,power.draw,power.limit,utilization.gpu --format=csv,noheader,nounits
# 另：CPU temp via thermal zones / sensors；CPU freq via scaling_cur_freq
cat /sys/class/thermal/thermal_zone*/temp
```

Throttle reason 細分字段（NVML standard，GB10 driver 580+）：
`clocks_throttle_reasons.idle`、`.applications_clocks_setting`、`.sw_power_cap`、`.hw_slowdown`、`.hw_thermal_slowdown`、`.hw_power_brake_slowdown`、`.sw_thermal_slowdown`、`.sync_boost`。

## 4. ⚠️ GB10 / DGX Spark 熱降頻突出嘅嘢（研究確認）

- **節流線 ~96–97°C**（EC/韌體更新後有節流問題討論；規格理想操作 5–30°C）
- **兩個已知異常**：
  1. **卡死低時脈 bug**（`sm_clock < 0.45×max` 而 util 高、power <35W、throttle reasons 無）—— 疑似 USB-C PD 供電故障（sparktop / spark-gpu-throttle-check）→ **警報**，唔係熱
  2. **GPU 卡 15W/650MHz loop + T Limit 50°C** 個案（NVIDIA forum）—— 人工 T-limit 太低做成
- **風扇由 EC 控制**：`fan.speed` 喺 nvidia-smi 常 N/A；要睇風扇 RPM 睇 EC（OS 未必 expose）→ 散熱主要靠`限 cap 監測 + 環境散熱

## 5. 其他熱控制研究要點（research 補充）

| 面向 | 要點 |
|---|---|
| **Thermal zones 分佈** | spark_hwmon 暴露 `tj_max`/`cpu_e_clu0/1`/`cpu_p_clu0/1`/`gpu`/`soc` —— CPU 同 GPU 夾埋睇（UMA 機 CPU 熱會頂到 GPU throttle） |
| **熱–功率 joint** | GPU temp >80 起要睇；>92 warn；>96 crit（緊貼節流線） |
| **長時間節流史** | 用 `throttle_reasons.active` event 記 timeline：幾時開始 throttle、維持幾耐、幾時解除（log 做 `throttle_duration`）—— 唔好淨 snapshot |
| **EC 風扇** | fan RPM / EC firmware 純 OS 未必讀到——唔好 reliance；用溫度+節流做proxy |
| **被動 vs 主動** | 主動 throttle check（cuBLAS load，`spark-gpu-throttle-check`）會load GPU——**唔好喺 production 行**；用被動矩陣 + 負載時觀察 |

## 6. 建議收（每節點，fast tier）

- GPU：`temperature.gpu`、`clocks.current.sm`、`clocks.max.sm`、`throttle_reasons.active` + 細分（thermal/power）、`power.draw/limit`、`utilization.gpu` ⭐
- 匯出 `clock_utilization_ratio`、`thermal_downclock`（bool：temp>80 AND clock ratio<0.8）、`power_cap`（bool：sw_power_cap set）
- 系統：`tj_max`/`soc`/`gpu` thermal zones；CPU `scaling_cur_freq` ⭐
- **throttle timeline**（event log：開始/持續/結束）＋ `throttle_duration_accum`

---

## 7. 🚨 警報（熱/降頻）

| 警報 | 邏輯 | 嚴重度 |
|---|---|---|
| **GPUHot** | `temperature.gpu > 92` | warn |
| **GPUThrottleLine** | `temperature.gpu > 96`（節流線） | crit |
| **ThermalDownclock** | `temp > 80` AND `clock_ratio < 0.8` AND util 高 | crit |
| **ClockCollapse**（卡死 bug） | `clock_ratio < 0.45` AND util>50% AND power<35W AND throttle_reasons==0（hysteresis） | crit |
| **PowerCap** | `sw_power_cap` set 持續 | warn |
| **ProlongedThrottle** | throttle_reasons active > X min | warn |

---

## 8. 一句總結

**判熱降頻要睇矩陣（四樣夾埋）：溫度 + SM 時脈比例 + throttle reason 邊隻 bit + 負載。** throttle reason 係最關鍵——分到「熱」（`hw/sw_thermal_slowdown`）vs「功率」（`sw_power_cap`）vs「GB10 卡死」（無 reason 但 clock <45%）。
